# Cloudflare deployment

## Architecture

The vinext App Router application runs as one Worker. Static files are served by
Workers Assets. Drizzle accesses the `DB` D1 binding directly; there is no connection
pool or database URL. CRUD operations use the Drizzle schema, and analytical queries
use bound SQLite SQL. Multi-statement writes that must succeed together use D1 batch.

This is a self-hosted edition. Do not set `CLOUD_MODE`: that variable belongs to
Umami's commercial hosted service, not Cloudflare Workers.

## Production instance

This checkout targets `https://umami.xingkaixin.me`, the `umami` Worker, and its
dedicated `umami` D1 database. `wrangler.jsonc` contains the production account,
database ID, and Custom Domain. Both `workers.dev` and preview URLs are disabled.
Commands with `--remote` operate on this production database; local development
continues to use `.wrangler/state`.

Production secrets and the initial administrator credentials are stored outside
the repository in `~/.config/umami/umami.xingkaixin.me/`, with owner-only file
permissions. Back up `worker-secrets.json` securely. The initial password in
`admin.json` should be replaced after first login, then removed from that file.
Do not copy the local development database or its test password into production.

## Local setup

Use Node.js 24 and pnpm 11. Install dependencies with `pnpm install`. The approved
`workerd` install script supplies the local Workers runtime.

1. Copy `.dev.vars.example` to `.dev.vars`.
2. Generate two independent secrets with `openssl rand -hex 32`. Put one in
   `APP_SECRET` and the other in `TWO_FACTOR_ENCRYPTION_KEY`.
3. Run `pnpm db:migrate:local`.
4. Set `UMAMI_ADMIN_PASSWORD` in your environment, then run
   `pnpm db:create-admin --local`. `UMAMI_ADMIN_USERNAME` optionally overrides `admin`.
5. Run `pnpm dev`, or `pnpm build && pnpm start` to preview the production Worker.

The production preview uses the same `.wrangler/state` as local migrations. A
`--config dist/server/wrangler.json` command without the configured `--persist-to`
would create a different local database under the build directory.

There is no default `admin/umami` account. Builds never apply migrations, create
accounts, or connect to a remote database. Never commit `.dev.vars` or `.wrangler`.

## First deployment

For a separate instance, these commands create resources in your Cloudflare
account. Check `wrangler whoami` and choose a distinct Worker and database name
before proceeding. Do not repeat initial setup against the existing instance.

```sh
pnpm exec wrangler login
pnpm exec wrangler whoami
pnpm exec wrangler d1 create umami
```

Replace `database_id` in `wrangler.jsonc` with the returned ID, and update `name`,
`account_id`, and `routes` for the new instance. The binding name stays `DB`.

Configure stable production secrets. Save them outside this repository; losing
`TWO_FACTOR_ENCRYPTION_KEY` makes stored authenticator secrets unreadable, and
changing `APP_SECRET` invalidates signed tokens and changes derived visitor IDs.
Create a private JSON file containing only these two keys, each with its own
value generated by `openssl rand -hex 32`. Never commit this file.

```sh
pnpm db:migrate:remote
# Supply a strong UMAMI_ADMIN_PASSWORD in the environment first.
pnpm db:create-admin --remote
pnpm build
pnpm deploy:check
pnpm exec wrangler deploy --config dist/server/wrangler.json --secrets-file /absolute/path/worker-secrets.json
```

`deploy:check` bundles the already built Worker without deploying it. `deploy`
builds and deploys using the vinext Cloudflare CLI. Remote deployment still needs
valid Cloudflare authorization and a real database ID. This repository does not
create remote resources automatically. The first deployment above uploads code
and secrets together; subsequent `pnpm deploy` runs preserve existing secrets.
Keep the Custom Domain in `wrangler.jsonc` so future builds retain the binding.

After deployment, sign in, create a website, install its tracker, and verify a
pageview and a custom event in the dashboard. Set up 2FA before exposing an
administrator account widely.

## Configuration

Runtime values belong in Worker vars or secrets. UI/build values such as
`BASE_PATH`, `API_URL`, `COLLECT_API_ENDPOINT`, `TRACKER_SCRIPT_NAME`,
`DEFAULT_LOCALE`, and `DEFAULT_CURRENCY` must be present when building. Keep
matching runtime values consistent when a setting is also returned by `/api/config`.

`APP_SECRET` is required. The 2FA key is optional only if you do not enable or
require 2FA. `LOG_QUERY=1` logs SQL and parameter counts for diagnostics; do not
leave verbose query logging enabled in normal operation. Framework error logs may
include bound values, so restrict access to logs.

Collection reads geographic information from Cloudflare's trusted `request.cf`
metadata. A supplied payload IP has no geographic lookup. There is no local
MaxMind database or arbitrary third-party geolocation lookup. The default client
IP header is `cf-connecting-ip`; configure `CLIENT_IP_HEADER` only when you control
and trust the proxy setting that header.

## Database semantics and limits

- Timestamps are stored as UTC ISO text and converted to `Date` in typed CRUD.
  Timezone aggregation uses explicit offset transitions, including daylight saving.
- Fixed-point values use decimal text to preserve storage precision. Analytics
  arithmetic and API chart values use SQLite/JavaScript floating point.
- UUID and string IDs are text; booleans are integers; JSON is text; replay chunks
  are compressed blobs. Replay chunks above 1,900,000 compressed bytes are rejected
  before insertion to leave room below D1's row limit.
- Ingestion splits property rows to stay below 100 parameters per SQL statement,
  while keeping the event, its properties, and revenue in one atomic D1 batch.
- Continuous percentiles are calculated with SQL window functions and interpolation.
- D1 has no built-in PostgreSQL regular expression operator. Regex filters use
  RE2-compatible matching over scoped distinct values, then bind the matches back
  into SQL. Backreferences and lookaround are not supported. Queries exceeding
  50,000 distinct candidates or 1 MB of matched values fail explicitly. SQLite
  `LIKE` case folding is ASCII-only, which differs from some PostgreSQL collations.
  D1 also limits `LIKE`/`GLOB` patterns to 50 bytes; long wildcard searches need
  shorter patterns or the supported regex filters.
- There is no automatic sharding, read-replica session routing, pre-aggregation,
  background queue, or historical data retention job. Long raw-event scans and
  replay storage can become expensive before other limits are reached. Monitor
  D1 rows read/written and database size; benchmark representative traffic.

Cloudflare documents the current [D1 limits](https://developers.cloudflare.com/d1/platform/limits/)
and [D1 pricing](https://developers.cloudflare.com/d1/platform/pricing/).
A paid Workers plan does not make D1 storage and scans unlimited.

## Existing PostgreSQL data

The D1 migration creates a new database; it does **not** import PostgreSQL data.
Do not run a PostgreSQL SQL dump against D1. An import must map timestamps, decimal
values, JSON and binary recordings to the schema in `src/db/schema`, preserve IDs,
and verify counts and report totals before switching the tracker endpoint.
Back up the old database and keep the old deployment available until validation
finishes. A tested historical-data importer is not included in this change.

## Verification and updates

```sh
pnpm test
pnpm check-types
pnpm build
pnpm deploy:check
```

The D1 test project runs against workerd/Miniflare, not an ORM mock. Existing UI
unit tests and Playwright tests cover separate parts of the app. To run Playwright
against the production preview, set `PLAYWRIGHT_BASE_URL`,
`PLAYWRIGHT_SKIP_WEB_SERVER=1`, `UMAMI_PASSWORD`, and `UMAMI_USER_ID` to your local
administrator details. Use a dedicated local database: tests create and delete data.
Stop the preview before rebuilding it or running `seed-data`; restart it afterward.
Separate local workerd processes must not write the same persisted D1 database
concurrently. `pnpm seed-data --days 1` adds demo data to the local database only.

Schema changes go through `pnpm db:generate`; review the generated SQL, back up
production data, and apply migrations explicitly before deploying dependent code.
Do not regenerate the initial migration after it has been used in production.
